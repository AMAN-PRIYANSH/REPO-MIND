# Evaluation plan, metrics and baselines

This document combines the originally proposed `EVALUATION_PLAN.md` and `METRICS_AND_BASELINES.md`. Datasets are described in [dataset strategy](DATASET_STRATEGY.md).

## Questions the evaluation must answer

1. Does each reachability method avoid false `NOT_REACHABLE` on cases with known truth?
2. Does combining two methods with abstention reduce wrong verdicts, and at what abstention cost?
3. Mode 1: can a local LLM, given the full fix diff, beat "every changed function"? Does lifting help?
4. Mode 2: which retrieval configuration ranks the true vulnerable function highest, and is any of it better than simply searching commit messages for the CVE/GHSA ID?
5. Mode 2: does an agent beat the best fixed retrieval pipeline, and at what time cost?
6. Do results hold on advisories created after the model's training cutoff?
7. On real applications, how often is the final verdict correct, and how often does the system abstain?

## Metrics

### Reachability (D2, D3)

- 3×3 confusion matrix: truth against output (REACHABLE / NOT_REACHABLE / CANT_DETERMINE).
- **False NOT_REACHABLE rate**, reported first in every report.
- Precision and recall of `REACHABLE` and `NOT_REACHABLE` among answered cases; coverage (fraction answered); selective accuracy.
- Accuracy alone is never reported.

### Retrieval (D4)

Gold = candidates whose symbol is a curated core symbol.

- Recall@1, @5, @10, @20 (any gold candidate in the top k).
- MRR (mean reciprocal rank of the first gold candidate).
- nDCG@10.
- All reported overall and split by candidate-set size (≤ 10, 11-100, > 100), because small sets are easy for everything.
- Cases whose gold symbols are not in the candidate set are reported separately as a ceiling limit, not counted as retrieval failures.

### Symbol identification (D1, D4)

- Precision, recall, F1 per case (macro-averaged); exact-set match; any-hit rate.
- Secondary scoring against core ∪ derived symbols.
- Split by advisory `created` date before / after the evaluated model's training cutoff.

### Agent (D4)

- Same symbol metrics as above.
- Steps used, stop reasons, invalid-answer rate, wall time per case, tokens per case.

### Evidence correctness (D2, D3)

- Verified-path rate for `REACHABLE`; verifier rejections and reasons.
- D3: owner adjudication of each `REACHABLE` path (correct / infeasible / wrong).

### Cost and resources

- Money: must be zero; any non-zero spend is a failure.
- Wall time per stage (p50, p95), GPU type used (Colab) or CPU, peak memory of the Go helper.

### Uncertainty

- 95% bootstrap confidence intervals with raw counts for every rate.
- Differences are called improvements only if intervals clearly separate; otherwise "no clear difference".

## Contamination controls

- D1 and D4 split by the report's `source.created` date relative to the evaluated model's published training cutoff.
- Headline numbers use the post-cutoff split; pre-cutoff numbers are labelled as possibly contaminated.

## Reproducibility requirements

- Every run records: repository commit, vulndb commit, Go / x/tools / Python versions, model names and digests, prompt template versions, seeds, hardware.
- Model outputs (LLM responses, agent traces, embeddings or their checksums) are cached; reports are generated by code from result files.
- `docs/results/` summaries are committed only when reproducible from committed artefacts.

## Gates

A result may be cited in the README or an interview only after it ran on the full planned dataset, its report includes counts, intervals and failure examples, and the owner has read at least five individual case outputs.
