## Limitations

- Five applications are case studies, not a sample of Go software: rates below describe these cases only.
- Cases of one application share code, toolchain and dependencies, so they are not independent; Wilson intervals assume independence and therefore understate the uncertainty.
- The adjudication judges the call path (reachability), not exploitability. It is NOT expert human ground truth: two independent Claude reviewer agents read the source at the pinned versions and agreed on every case, the supervising assistant reconciled them and re-read two key claims, and the owner spot-checked a fixed sample of path steps (reviewer files in docs/results/cp7b/adjudication_reviews/). The reviewers are language models related to the system's builder and not independent of each other in their blind spots; the supervisor also reviewed the system.
- INFEASIBLE_PATH judges the path shown (changed targets first), not the target: the reviewers' notes record that for several REACHABLE cases the target looks reachable by another path that the system did not show. Precision here is therefore the rate at which the shown path is correct, not the rate at which the target is truly reachable.
- Applications are pinned to releases from 2025 or earlier (selection rule A3); their current versions may differ.
- Selection rule V1 requires a GitHub fix commit, which excludes most golang.org/x advisories (fix links are go.dev/cl); D3 therefore says nothing about those.
- Mode 1 targets are every function the fix commit changed, at the fix commit's parent. When the application's dependency version is older or newer than that parent, a target can be missing (an ERROR, so CANT_DETERMINE) or can differ from the code the application really uses.
- Analysis is for linux/amd64, CGO_ENABLED=0, no build tags; other build configurations can differ.
- govulncheck is a reference, not truth: it checks the advisory's exported symbols, while Mode 1 checks the changed functions, so the two answer related but different questions.
